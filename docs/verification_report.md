# 追加发现（不属于 A-D 编号，但影响可实现性）

## E1. 概率命中取整：design 用 `round`，spec 默认 `ceil`（数值不同的分支）

- design_v1.md:63（R3 需求行）`0<D<1 取 1 且按 **round(D*100)%** 命中`
- design_v1.md:336 `0 < D < 1 → 命中率 = **round(D*100)%**，命中则造成 1 点`
- design_v1.md:356 `命中率用 **round(D*100)%**（0.65 → 65%，0.005 → 1%…），再用 `rng.randf()*100 < 命中率` 判定`
- spec_rules.md:113 `hit_pct = clamp(**ceil(D_milli / 10)**, 1, 99)`
- spec_rules.md:229-230：`ceil` 默认 vs `round_half_up` 备选，表内 `D_milli=11 → 2% / 1%`、`114 → 12% / 11%`
- 实算：D_milli ∈ 1..999 中两者不同的比例 = **401/999 = 40.1%**；具体分歧例：`D_milli=11 → ceil 2% vs round 1%`、`114 → 12% vs 11%`；另外 `round` 不加 clamp 时 `D_milli=1 → 0%`、`999 → 100%`，与 spec 的 `[1,99]` 钳制行为不同。
- **严重度：高（列入阻断级 B-1）**。spec §13.3 第 2 条验收向量（:718）会与 design 的写法冲突。

## E2. 随机数口径：Godot `RandomNumberGenerator` + 浮点比较 vs 自研 LCG + 禁浮点

- design_v1.md:197（ADR-5）`随机数用**显式种子**的 `RandomNumberGenerator`，种子写入存档与战斗日志`
- design_v1.md:356 `再用 `rng.randf()*100 < 命中率` 判定`（浮点比较决定分支）
- spec_rules.md:23 `内部**全部整数运算**…**禁止用浮点比较决定任何分支**`
- spec_rules.md:658-660 `state = (state * 1103515245 + 12345) mod 2^31` / `roll_1_to_100 = ((state >> 16) mod 100) + 1`（自研 LCG，状态恒 < 2^31）
- data_schema.md:298 `"rng_state": 9918273645` —— 实算 `9918273645 > 2^31−1 = 2147483647`，**不是该 LCG 的合法状态**；data_schema.md:297 只约束了 `rng_seed ≤ 2^53-1`，而 spec 未定义 seed→state 的换算。
- 影响面：design_v1.md:457（M0.5 导出 golden_vectors）、design_v1.md:462（M1 逐条对账）、design_v1.md:423/486（存档往返含 RNG 状态）都以"跨语言可复现"为验收标准；Python 原型若按 spec 的 LCG、GDScript 若按 Godot RNG，黄金用例不可能逐条一致。
- **严重度：高（列入阻断级 B-3）**

## E3. 单位口径：spec §2.2 的 `P_cur * 1000` 隐含"点"，data_schema §6 存"千分比"

- spec_rules.md:24 `属性表的整数（如力量 9）在管线内展开为 9000‰`
- spec_rules.md:99 `p_milli = atk.P_cur * 1000 + 2000 * n      # 步骤 1：精力加进力量`（**若 P_cur 已是 9000，这里得到 9,000,000**）
- spec_rules.md:119 `def.P_cur = max(0, def.P_cur - damage)`（按点扣减，与上式自洽）
- spec_rules.md:160 `A_cur、P_cur 同样 clamp 到 [0, 999]`（按点语义合理，按千分比语义则会把 9 点截成 0.999 点）
- data_schema.md:7 `数值内部统一用整数千分比…`spec_rules.md` 里写的 `力量 9`（**点**）= 内部 `9000‰``
- data_schema.md:184 `"power": 9000,               // = 力量 9 点（剑士）`
- 实算演示：读 UnitState 的 `power = 9000`，按 spec:99 计算 → `9000 × 1000 = 9,000,000`（差 1000 倍）。
- **严重度：高（列入阻断级 B-8）**：建议 spec §2.2 把伪代码改成显式的单位转换（`P_milli_in = atk.P_cur`，若 `P_cur` 以点存则 `×1000`），或统一规定 `P_cur/A_cur` 一律以千分比存储并在伪代码中不再乘 1000；同时把 §2.5 的 `[0,999]` 改为 `[0, P_max_milli]`。

## E4. 附录 A2 的"用户原稿数字自洽"结论不成立

- appendix:46-47 `目标 TTK = 2.5-3 次 → 护甲/力量 ≈ 0.65-0.70（R=0.2）。这正是用户原稿里 力量 12 / 护甲 8 / 物抗 35% 的比例（0.67），**说明原稿的示例数字本身是自洽的**`
- spec_rules.md:478（C2）重复同一结论。
- 实算：`A/P = 8/12 = 0.667` ✅，但原稿的物抗是 **35%**，不是 0.2：`TTK = (1−0.35)/(1−0.667) = 0.65/0.3333 = **1.95** 次`（E[D] = 6.154，12/6.154 = 1.95）。同表在 ratio 0.667 处：R=0.2 → 2.40、R=0.35 → 1.95、R=0.4 → 1.80。也就是说，按原稿数字实算的 TTK **低于目标 2.5~3，落在 A7 警告的"先手即胜负"区间**（A2 自己把 ratio 0.4 的 1.3 次称为"退化成谁先手谁赢"）。
- 另外原稿 R=35% = 350‰ **超过 spec §9.4 DR1 的"任何单位物抗 ≤ 300‰"**（spec_rules.md:502）与 appendix:65 的"必须硬限制 `R ≤ 0.4`"，三处 R 上限口径（600‰ 硬钳制 / 300‰ 设计规则 / 0.4 上限）并存。
- **严重度：中**：建议把 A2 的"原稿自洽"改为"原稿的护甲/力量比 0.67 落在目标区间，但其物抗 35% 使实际 TTK 降到 1.95，需把物抗调到 ≤200‰ 才自洽"，并把 R 上限的三处口径统一表述（硬钳制 600‰ / 设计目标 ≤300‰）。

## E5. 规格未覆盖关卡胜负条件（SURVIVE_ROUNDS / REACH）

- design_v1.md:392 `关卡可附加条件（v1 第 3 关用"守住 N 回合"）`；data_schema.md:145-146 `victory: int  # Victory.ANNIHILATE / SURVIVE_ROUNDS / REACH` + `victory_param`
- 但 spec §7（:408-417）的胜负判定只写 `胜利 | 一方全部阵亡（力量池归零…）` 与 30 回合超时规则，**没有任何"守住 N 回合即胜"的判定时点与优先级**（与 30 回合上限、存活数判定的关系也未定义）。
- **严重度：中**：建议 spec §7 增补 victory 枚举的判定规则与优先级。

# 给 lead 的三句总结

1. **算式层面这份文档集是可信的**：spec v1.1 的 §2.6.2 三模式表、§2.7 的 16 格概率表（我独立复现 **16/128**，平地 **0/64**）、§10.1/§10.3 全 112 格、§10.2 全 64 格 TTK、§10.4 的 0/8/26/48 与 2/26/54/64、§9.1 的 8 个镜像 TTK、§6.2 的 45 格射程表，以及附录 A2 的比例表与 A7 的 300 场模拟（我实跑探针，逐项吻合），全部用 Python 复算通过；tech_feasibility 的两个下载体积我也用 HTTP HEAD 独立复测，字节数与文档**完全一致**（86,013,866 / 1,281,349,702）。
2. **但"文档之间"有 8 处硬冲突会让实现者写错代码**：概率命中的 round/ceil（40.1% 的取值不同）、行动顺序三方不一致且 `initiative` 无数据、RNG 用 Godot `RandomNumberGenerator`+浮点还是自研 LCG、存档缺 `energy_used_this_turn` 等字段、升级阈值"每级清零 15 杀"还是"累计 8 杀"、附录护甲池数 23/52（正确是 26/54）、design §7 的 `R=0.9→D=20` 与钳制后 `D=5`、以及 `P_cur` 是点还是千分比（差 1000 倍）；这 8 条已列成阻断级清单，均有行号原文与实算数字。
3. **残余的历史错误比预想的多一处**：lead 那个"力量线无法一击秒杀"的旧结论确实已在 appendix:125 与 spec:587 更正为 48/64（我复算确认），但同源的旧尺度数字仍在两处流动——spec:479（C3）与 design:542（Q10）的 `+86% / E[D] 8.75→16.25 / 力量 16 尺度`（v1.1 下应为 +67%（P=9）、3.33→10.00），附录 A4 的示例 `1.111→0.444 / 1.250→0.125` 与 23/192 也不属 v1.1 表；另外 appendix A2 的"用户原稿 12/8/35% 自洽"经实算是 **TTK=1.95**、并非自洽（目标 2.5~3）。**建议：修完 B-1~B-8 与这三处旧尺度残留后，文档集可以交给用户；在此之前，用户若照 design §7 的 R=0.9 用例或附录 A5 的表格做决策，会得到错误结论。**
