> ## 仍然有效、有约束力的部分
>
> 1. **分层铁律**：`view → ai → core`，core 绝不反向；core 不 `extends Node`、不 `get_node()`、不碰渲染。
>    （现状核实：`game/src/core/` 21 个文件全部 `RefCounted`，零 `get_node()`，方向正确 ✓）
> 2. **取整三件套**：伤害 `floor`、倍率连乘 `round_half_up`、命中率 `ceil`。不得混用。
> 3. **定点数千分比**：内部一律整数千分比（力量 41 → 41000），禁浮点比较。
> 4. **确定性**：32 位 LCG（`RngService`，禁 Godot 内建 RNG），seed 决定一切；同一 seed 的动作序列必须可复现。
> 5. **`preview` 与 `resolve` 必须共用同一份公式**（现状：`Rules.preview` / `Rules.resolve` 同源 ✓）。
> 6. **`miss`（没打中）与 `damage`（打不动）必须分开**；事件字段只许加、不许改名。
> 7. **命名与度量**：`snake_case.gd` / `PascalCase` / `UPPER_SNAKE`；坐标 `Vector2i(x, y)`；"格数"一律曼哈顿距离。
> 8. **同一算法全局只有一处实现**。
> 9. **物抗 / 魔抗不可加点**；魔抗至今不参与结算（预留）。

### C2/C3 的直接后果：新的伤害与档位表（实算，非估算）

`D = (力量-护甲) × (1-物抗)`，单位：点。**只有 `0 < D < 1` 才进入概率判定**。

| 力量−护甲 | 无(0) | 低(0.2) | 中(0.4) | 高(0.8) | 免疫(1.0) |
|---|---|---|---|---|---|
| 1 | 1 | 0.8 → **80%** | 0.6 → **60%** | 0.2 → **20%** | 0 |
| 2 | 2 | 1.6 → 1 点 | 1.2 → 1 点 | 0.4 → **40%** | 0 |
| 3 | 3 | 2.4 → 2 点 | 1.8 → 1 点 | 0.6 → **60%** | 0 |
| 4 | 4 | 3.2 → 3 点 | 2.4 → 2 点 | 0.8 → **80%** | 0 |
| 5 | 5 | 4.0 → 4 点 | 3.0 → 3 点 | 1.0 → 1 点 | 0 |
| 10 | 10 | 8.0 → 8 点 | 6.0 → 6 点 | 2.0 → 2 点 | 0 |

**五档的等效耐久倍率**（对纯力量输出者）：

| 档位 | 减伤 | 伤害乘数 | 等效耐久 |
|---|---|---|---|
| 无 | 0 | ×1.0 | ×1.00 |
| 低 | 0.2 | ×0.8 | ×1.25 |
| 中 | 0.4 | ×0.6 | ×1.67 |
| 高 | 0.8 | ×0.2 | **×5.00** |
| 免疫 | 1.0 | ×0 | **不可击杀** |

> **平衡提示（重要的设计约束）**：档位之间的跳跃极大（低 → 高 是 **4 倍**耐久），而升级每级只有 +3 点属性。所以：
> 1. **物抗档位应该用来表达"兵种身份"**（民兵无抗、剑士低抗、石肤守卫高抗），**不要**用它做成长曲线；
> 2. 八兵种全矩阵实算后有 **8/64（12%）** 的组合落在概率判定区间，主要集中在"剑士/塔盾卫打低抗单位"与"破甲者/石肤守卫/掷弹手打高抗单位"这两类对抗上——**这正是概率判定应该出现的地方**（以弱打强、以强打肉）；
> 3. **TTK 旋钮现在有两个**：`TTK = 力量 / ((力量-护甲)×(1-物抗)) = [1/(1-物抗)] × [力量/(力量-护甲)]`。物抗档位是独立倍率，护甲/力量比是另一个。平衡时先按"C2 档位表"定身份，再调护甲把 TTK 压进 2.5-4 命中。

### C5 的处理（免疫档）

- **v1 的普通关卡与敌人不使用免疫档**；它只作为 v2「Boss 机制/需要特定解法」的预留。
- 若坚持在 v1 使用，必须同时满足：① 给玩家提供至少一种**魔法技能**；② 关卡里给出明确提示（"这个单位免疫物理"）；③ 它的力量池不能太大，否则战斗会变成拖时间。**这三条不满足时，请把该单位设为"高"档（0.8）而不是"免疫"。**
- `mag_res` 同理保留五档，v1 只有 UI 显示（灰色标注"魔抗（v1 未启用）"）。

| 问题 | 结论 |
|---|---|
| 用什么架构 | **Godot 4.7.2（GDScript）+ 3D 场景 + 正交固定角度相机（2.5D）+ 单线程 Web 导出为首发目标**，同一套代码可导出 Windows 桌面版 |
| 为什么不是纯网页（Three.js/Babylon） | 网页栈能做，但要从零自建场景图/UI/动画/粒子的"塔"。`tech_feasibility.md` §8 逐项估算了净额外成本：**8-18 人天（估算值，非实测）**；Godot 六维打分 27/30 vs 纯 Web 22/30 |

| v1 范围 | 完整战棋规则 + 一个可循环的游戏流程（主菜单 → 选关 → 战斗 → 结算 → 升级加点 → 存档 → 读档继续）+ 简易 AI + 多存档槽 |

### 已定案的最关键一条：物抗是"真减伤"，公式是乘算

原文写的是 `伤害 = (力量 - 护甲) / (1 - 物抗)`，但用户在第二轮澄清里给出算例：**力量−护甲 = 2、物抗 0.8 → 0.4 → 40% 造成 1 点**。这只有在 **`D = (力量-护甲) × (1-物抗)`** 下成立（`2 × 0.2 = 0.4`）。

因此 **`res_mode` 默认 = `MULTIPLY`**：物抗越高，挨打越轻（符合直觉，也是"物抗"这个名字该有的语义）。
`DIVIDE` / `FLAT` 两个模式作为配置项保留（改一个枚举即可切换），但**不作为默认值**。

> 详细后果、五档档位表与平衡约束见 **§0.5**（规则澄清增补）。`spec_rules.md` 的 §1/§2/§9/§10 正在按 v1.2 同步；在它完成前，**以 §0.5 为准**。

## 2. 架构决策（ADR）

### ADR-1：引擎选 Godot 4.7.2（GDScript），而不是纯网页或命令行

**决策**：用 **Godot 4.7.2 stable**（2026-08-18 发布；4.8 尚为 dev7，v1 不用）开发，GDScript 主力语言，3D 渲染管线，导出 **Web（WASM，单线程）+ Windows 桌面**。版本号锁死写进 README 与导出预设，避免 minor 版本破坏性变更（`tech_feasibility.md` R13）。

**理由（按权重排序）**

1. **2.5D 与动画是引擎的强项，不是我们的工作量**。战棋的"2.5D"本质是"3D 场景 + 固定/正交相机"。Godot 一次给齐：场景图、相机、光照阴影、粒子、Tween、Control UI、输入映射、音频总线、资源系统。用 Three.js/Babylon.js 要达到同等效果，需要自己搭 UI 层、动画调度、资源加载、输入与寻路集成——这是**数周级的额外成本**，且是纯苦工。
2. **无美术资源下的表现力，靠程序化**。Godot 内置 `BoxMesh/SphereMesh/CapsuleMesh/CylinderMesh/PrismMesh` 等图元、内置 `Tween/AnimationPlayer`、`GPUParticles3D`、CanvasLayer 伤害数字，都是零素材可用；纯网页栈里这些都要手写。
3. **规则层可独立测试**。Godot 的 `--headless` 可以在无显示器环境跑 GDScript，因此战斗规则（公式、命中、升级、存档）能做单元测试，**不需要跑浏览器、不需要逐帧截图验证**。这是本项目最重要的工程保障（见 §7）。
4. **与 R13 契合**。Godot 的"场景 + 资源 + 信号"模型天然适合"战棋作为 RPG 子模块"：外层 RPG（地图探索、对话、背包）以后加场景即可，战棋是一个可被 `BattleScene` 调用的独立场景，输入是一个 `BattleSetup` 资源，输出是一个 `BattleResult` 资源。
5. **分发**。Web 导出满足"网页"诉求（用户不需要装程序就能玩）；桌面导出满足"以后上 Steam / 本地分发"。

**代价与缓解**

| 代价 | 缓解 |
|---|---|
| 本机环境**已完成** | Godot **4.7.2 绿色版** + Web 导出模板已装好；headless 测试、2.5D 截图、Web 导出**三步都已跑通**。环境不需要你再做任何事，你只要会用编辑器按 F5（见 `docs/godot_handbook.md`） |
| **Web 上只能用 Compatibility 渲染器**（Forward+ 与 Mobile 在 Web 均不可用，因为只支持 WebGL 2.0 且 Godot 无 WebGPU） | 画质方案按 Compatibility 能力表设计（见 ADR-3），不依赖 TAA/SSAO/贴花/体积雾等不可用特性 |
| **iOS Safari OOM**：Godot 默认 `WASM_MEM_MAX=2048MB`，iOS 16.2 直接 OOM（官方 issue #70621 至今 open） | 编译降低 `WASM_MEM_MAX`（官方报告 256MB 可解），或 v1 明确"iOS 请用 Chrome/Firefox"；移动端列为"尽力支持"而非验收目标 |
| GDScript 是动态类型，重构手感弱于 TypeScript | 关键数据用 `class_name` + 强类型标注 + `RefCounted` 资源类；规则层写单元测试兜底；GUT / gdUnit4 均为活跃框架可选 |
| 以后想改成别的引擎，迁移成本 | **规则层与表现层严格分离**（§5），规则层不引用任何节点/渲染 API；M0.5 还会产出语言无关的"黄金测试向量"，迁移时可逐条对账 |

**被否决的方案**

- **纯命令行 / 文字游戏**：无法实现 R10（方向+力度的抛物线瞄准），也无法满足"2.5D 和动画"的诉求。**一票否决**。
- **纯网页（TypeScript + Three.js/Babylon.js）**：可行且工程体验好（Vite + Vitest + 天然可测），体积小两个数量级（three r186 gzip 仅约 180 KB），但要自建引擎层——`tech_feasibility.md` §8 逐项估算净额外 **8-18 人天**。本项目只有一个人、没有美术资源，选"引擎自带得多"的那条路。若用户更看重"纯前端技术栈/无引擎构建步骤"，这是唯一值得换的备选（切换点：§11 Q3），且 M0.5 的规则层产物**在两条路线下都可复用**。
- **纯 2D 像素/矢量（Godot 2D 或 Godot 2D + 伪 3D）**：伪 2.5D 需要 8 方向手绘或矢量素材，与 R12 冲突；且弹道抛物线在 2D 平面内会丢失"高度差"这个战棋乐趣点。**否决**。

### ADR-2：表现层配置——正交相机 + 四向旋转（2.5D 的落地方式）

| 项 | v1 取值 | 说明 |
|---|---|---|
| 投影 | **正交（Orthogonal）** | 无透视畸变、远近同尺寸，即经典 2.5D/等距观感 |
| 俯角 | **55°**（写进配置，可调 40-70°） | 太低看不到格子，太高接近俯视图失去立体感 |
| 偏航 | **四向（45°/135°/225°/315°）**，`Q/E` 旋转 | 固定角度让"格子-屏幕"映射稳定，便于弹道瞄准与鼠标拾取 |
| 缩放 | 3 档（近/中/远），滚轮切换 | 战斗中看细节 vs 看全局 |
| 平移 | WASD / 屏幕边缘 / 中键拖拽 | 相机跟随当前行动单位（可关） |
| 旋转过渡 | 0.25s Tween 插值 | 旋转时单位朝向标签自动转向相机（billboard） |

**为什么正交优于透视**：格子对齐、鼠标拾取、弹道落点的视觉判读都更稳定；且正交天然"像 2.5D 游戏"。

### ADR-3：无美术资源的表现方案（角色/地形/特效全部程序化）

这一节直接回答用户的"我没有任何美术资源"。

**A. 角色（每单位 3-6 个图元，全部代码组装）**

```
身体       CapsuleMesh   ← 按"护甲"值调粗细：护甲越高越粗壮
头         SphereMesh
武器/道具   BoxMesh / PrismMesh / CylinderMesh  ← 按攻击类型换形状
脚下标记    CylinderMesh（薄圆盘，半透明）        ← 阵营色 + 兵种形状
血条/能量   Sprite3D + 无贴图着色 或 3D 细长 BoxMesh
```

**在"没有立绘"的前提下保证可读性的三件事**（这是程序化美术的关键，不只是"能跑"）：

1. **形状语义**：近战 = 三角/棱柱，弹道 = 方块/筒状，远程 = 细长圆柱；肉盾 = 宽扁方块；高物抗单位 = 外层套一个线框球。
2. **颜色语义**：阵营色（我方蓝 / 敌方红）作用于脚下标记与轮廓；兵种等级用亮度/饱和度分级（1 级暗淡，5 级高亮）。
3. **状态语义**：可行动 = 脚下标记脉动；已行动 = 灰度化 + 标记熄灭；被选中 = 外发光（outline shader）；受伤 = 短暂闪白；阵亡 = 倾倒 90° + 淡出。

**B. 地形（程序化，不占磁盘，且要压住 draw call）**

- **用 `SurfaceTool` 把整张地形烘成单块 `ArrayMesh`**：格线用顶点色画进同一个网格，`12×12 = 144` 个格子从 144 个 draw call 压到 **1 个**（`tech_feasibility.md` §6.7 列为性价比最高的三项之一）。
- 地形高度按关卡数据的阶数生成（`0 / 1 / 2` 阶 = 0 / 0.5 / 1.0 世界单位）；高度差用侧壁面片表达，天然带出立体感。
- 高亮/可达范围：通过**顶点色或 `instance uniform` 改色**，不新增材质；范围高亮用一张贴地的半透明 quad 网格叠加。
- 不用 Decal（Web 下不可用）。

**C. 动画（全部代码驱动，无骨骼、无美术）**

| 事件 | 表现 | 实现 |
|---|---|---|
| 待机 | 上下浮沉 2-3 cm + 轻微摇摆 | `Tween` 循环 |
| 移动 | 沿路径做小跳弧线 + 朝向旋转 + 落地挤压 | `Tween` 链 / `Curve3D` |
| 近战攻击 | 前冲 0.12s → 接触 0.08s（缩放挤压）→ 回位 0.18s | `Tween` 序列 + 位移 |
| 远程攻击 | 蓄力（后仰 + 发光）→ 弹体飞行 → 目标命中闪光 | 弹体 = 小 SphereMesh 沿直线/曲线插值 |
| 弹道攻击 | **真实抛物线弹体**（用与规则层同一套物理参数） | 小图元 + 拖尾粒子 |
| 命中 | 目标闪白 + 抖动 + 伤害数字上浮淡出 | `ShaderMaterial` 改色 + `Label3D` |
| 未命中 | 弹道落点尘土 + 侧向偏移 + "MISS" 数字 | 粒子 + `Label3D` |
| 休息 | 呼吸放大 + 脚下恢复光环 + "+1 精力" 文案 | `Tween` + 环形粒子 |
| 阵亡 | 倾倒 90° + 缩放归零 + 淡出，格子标记熄灭 | `Tween` |
| 演出反馈 | 攻击命中/受击时相机抖动 0.1-0.2s、屏幕轻微闪红 | `Camera3D` 偏移 + `ColorRect` |

**D. 描边与氛围（可选开关，全部在 Compatibility 渲染器能力范围内）**

- **描边**：官方推荐做法是 `BaseMaterial3D.grow` + `next_pass` 的反转外壳（零贴图、零后处理，比手写后处理稳健）。**注意**：`tech_feasibility.md` §6.4 把"跨渲染器下视觉一致"标为**推测**，需在 M4 真机确认（若在 Compatibility 下效果不理想，退化为"用颜色/亮度区分阵营"即可，不影响可玩性）。
- **氛围**：柔和环境光 + 简单雾 + Glow（可选）。
- **明确不可用**（Compatibility 在 Web 下不支持，不要设计进去）：TAA/FXAA/SMAA、体积雾、SSR/SSIL/SDFGI、Decal 贴花、粒子拖尾、景深、计算着色器。
- 抗锯齿只有 **MSAA3D / SSAA** 可用；假阴影用贴地椭圆 `quad` 代替真实阴影贴图（省钱且不掉帧）。

> **一句话**：v1 的视觉目标是"干净的低多边形战棋"，靠**形状/颜色/动效/相机**传达信息，而不是靠贴图。用户后续任何时候补上美术资源，都是替换 `UnitVisual` 里的网格与材质，规则层一行不动。

### ADR-4：规则层与表现层分离（这是全案最重要的工程决策）

```
BattleSetup(资源) ──► BattleCore(纯逻辑, 无节点) ──► BattleEvent[](数据) ──► BattleView(节点/动画/UI)
                                 │
                                 └─► SaveService(JSON 存档)
```

- `BattleCore` 只依赖 `RefCounted`、数组、字典和定点数工具，**不 `extends Node`、不 `get_node`、不碰渲染**。
- 所有变化通过**事件数组**输出，例如 `{type="damage", target=3, amount=2, killed=false}`；表现层只是事件的"播放器"。
- 直接收益：
  1. `--headless` 下可对全部规则写单元测试（人肉试玩不能覆盖 0.65 概率命中的统计正确性）；
  2. 存档就是 `BattleCore` 状态的 JSON 序列化，与动画无关；
  3. RPG 外层以后可直接调用 `BattleCore` 做"自动结算"（跳过动画）；
  4. 想换渲染方案（甚至换引擎）时，逻辑层可以整体搬走。

### ADR-5：定点数数学与可复现随机

- 所有战斗数值内部用**千分比整数**（`力量 9`（点）→ 内部 `9000‰`），伤害公式在整数域计算并**显式规定取整方向**，避免浮点误差导致"同一局面两次结果不同"。
- **统一取整约定（以 `spec_rules.md` 为准，二者必须一致）**：
  - 伤害取整 = **向下取整 floor**；
  - 比例乘法（高低差、精力并入等）= **四舍五入 round-half-up**；
  - 概率命中的百分比 = **向上取整 `ceil(D_milli / 10)`**（`D_milli=5 → 1%`、`650 → 65%`、`999 → 99%`）。**注意这里不是 `round`**——`ceil` 与 `round` 在 1..999 中有 **401/999（40.1%）** 的取值不同，写错会导致 spec 的验收向量失败；
  - 全部比较在**整数域**完成，**禁止浮点比较**参与任何分支判定。
- **随机数**：使用**规格化的 32 位 LCG**（乘数/增量/状态全部是 32 位无符号整数，状态只占 `uint32`），而不是 `randf()` 之类的浮点抽样。原因：① 满足"禁浮点比较"；② 状态可完整写进存档；③ **跨语言可复现**——M0.5 的 Python 原型与 GDScript 实现用同一套参数就能产出逐条一致的黄金用例（这也是"跨语言对账"能成立的前提）。
- 种子（`prng_seed`，uint32）与状态（`prng_state`，uint32）写入存档与战斗日志；**不要用 Godot `RandomNumberGenerator` 的 64 位状态**——它无法与 Python 原型逐条对账，也可能超出 JS double 的安全整数范围（见 `data_schema.md` §9）。
- 价值：可复现 bug、可做"回放"、可写"给定种子必出预期结果"的测试、后续联机/对战也有基础。

## 5. 战斗流程与关键机制（v1 默认判定）

> 完整形式化规格与算例见 `docs/spec_rules.md`；这里只列决定"能不能做出来"的关键点。

### 5.1 一回合的结构

```
单位回合开始
 ├─ 状态结算（休息恢复的持续效果、精力上限钳制）
 ├─ 阶段 A：移动（可选，最多"移动力"格；路径按 4 向；进入敌方近战威胁格额外消耗 1 点）
 ├─ 阶段 B：动作（三选一 + 可叠加精力）
 │    ├─ 普通攻击：近战 / 弹道 / 远程
 │    ├─ 技能（v1 禁用占位）
 │    └─ 休息：恢复力量与护甲（各 X 点），精力 +1（≤上限）
 └─ 单位回合结束 → 下一个单位
```

- **移动不是必须的**；动作后不能移动（v1 取"移动先于动作"，理由：实现与 AI 都简单，且避免"打了就跑"导致战斗无限拖长）。
- **精力消耗在一次动作内结算**：一次攻击最多投 3 点，每点 +2 伤害；力量攻击时并入己方力量（即 `P' = P + 2k`，再代入公式），破甲攻击时直接加到破甲伤害上。跨回合不保留"未用额度"。

### 5.2 伤害结算（R3/R4/R6）

```
输入：攻击方力量 P、投入精力 k、目标护甲 A、目标物抗档 R、高低差系数 h（可选）
若 攻击类型 == 力量:
    P_eff   = round_half_up((P + 2k) * h)          # 精力并入力量后，再乘高低差（默认 h=1000，即无修正）
    delta   = P_eff - A
    D_milli = delta * (1000 - R) / 1000            # ★乘算：物抗 = 真减伤（整数除法 = floor）
    delta <= 0            → 无法造伤（事件 miss，原因 no_damage）
    D_milli <= 0          → 无法造伤（免疫档 R=1000 会走到这里）
    0 < D_milli < 1000    → 命中率 = ceil(D_milli/10)%，命中则造成 1 点
    D_milli >= 1000       → 100% 命中，造成 floor(D_milli/1000) 点
若 攻击类型 == 破甲:
    伤害 = 固有破甲伤害 + 2k        # 无视物抗、无视护甲、无视己方力量、无视高低差，必然命中；只打护甲池
```

> **取整三件套（必须与 `spec_rules.md` §2.1 完全一致，不得混用）**：伤害 `floor`；比例乘法 `round_half_up`；**命中率 `ceil(D_milli/10)`**。
> 注意最后一条：默认是 **`ceil`**（`D_milli=11 → 2%`、`650 → 65%`、`999 → 99%`），**不是 `round`**——两者在 1..999 中有 **401/999（40.1%）** 的取值不同。

**减伤模式（`BalanceConfig.res_mode`）**

| 模式 | 公式 | 含义 | 备注 |
|---|---|---|---|
| **`MULTIPLY`（v1 默认，用户澄清 C2）** | `(P'-A) * (1-R)` | **物抗 = 真减伤** | 用户算例：差值 2 × 高抗(1-0.8=0.2) = 0.4 → **40% 造成 1 点** |
| `DIVIDE`（备选） | `(P'-A) / (1-R)` | 按原文除式 | 会让物抗变成"物理易伤"，仅保留为配置项 |
| `FLAT`（备选） | `(P'-A) - R*P'` | 按攻击力比例削伤 | 备选 |

**一个有用的数学等价**：在 `0 < D < 1` 时，"以 `D` 为概率造成恰好 1 点"与"造成 `floor(D)` 点"的**期望值完全相同**（如 `D=0.65`：65%×1 = 0.65 = floor 意义上的期望）。所以**同一份期望可以用两种等价实现**：
- **严格字面实现**（v1 默认）：`if 0 < D_milli < 1000: damage = (rng_int(1..100) <= ceil(D_milli/10)) ? 1 : 0`；
- **余数掷骰实现**（备选 `REMAINDER_ROLL_WHEN_AUTO`）：`damage = D_milli // 1000; if 余数 > 0 and rng < 余数概率: damage += 1`。后者让 `D >= 1` 的对局也带概率判定（期望不变，但手感更"活"）。

两种实现都必须用**整数掷骰**（`rng_int(1..100) <= pct`），**禁止 `rng.randf()*100 < pct` 这类浮点比较**。事件层要保留区分（`damage` vs `miss(prob_miss)`），因为玩家需要看到"是没打中，不是打不动"。

**"命中与伤害计算独立"（R10）的落地方式**：弹道攻击分两步——先判定**落点是否覆盖目标**（几何命中），再用上面的伤害判定。因此弹道命中后仍可能"未造成伤害"（D≤0），也可能"命中但只按概率打出 1 点"。这与文档一致。

**概率命中的实现细节**：`D` 在整数千分比域内计算，命中率 = **`ceil(D_milli/10)` 个百分点，再钳制到 [1,99]**（`D_milli=650 → 65%`、`5 → 1%`、`999 → 99%`），判定用 `rng_int(1..100) <= 命中率`。必须写单元测试做**统计验证**（10 万次采样，容差 0.5%）。

### 5.3 弹道瞄准（R10 的落地难点）

文档要求：**玩家输入方向与力度，抛物线飞行，仅落地判定，无辅助瞄准 UI**。

v1 的输入映射（一套即可玩，且可调）：

```
① 玩家选中弹道单位并选择"弹道攻击" → 进入瞄准模式
② 相机切到"瞄准机位"（俯角略降低、视野略微拉高，仍为正交）
③ 玩家拖拽鼠标/按方向键设定：
     水平朝向 θ（8 或 16 个离散方向，或连续角度）
     仰角 φ（30°-75°，鼠标纵向拖拽映射）
     力度 p（0-100%，可由拖拽距离或按住的时长决定）
④ 发射：弹体沿初速度 v = f(p, φ) 做重力抛物线飞行（重力常数写进 balance.tres）
⑤ 落地（y ≤ 地面高度）时：判定落点格中心半径 r 内的所有单位
     r 由角色属性"落地命中判定范围"决定（升级可加，R5）
     命中 = 到落点的水平距离 ≤ r 且高度差 ≤ 容差
⑥ 对每个命中单位独立跑伤害结算（§5.2）
```

**关于"无辅助瞄准"**：v1 提供**只有发射方向的一条虚线**（仅显示朝向，不显示落点、不显示预测轨迹），弹道预览完全关闭。这是"无辅助瞄准"的严格执行方式。若试玩后发现太难，只需在 `aim_ui.gd` 打开 `show_predicted_arc` 开关（属 §11 Q2）。

**为什么用离散方位 + 连续力度/仰角**：纯自由三维瞄准在正交相机下判读极难，离散方位可保留"手动瞄准"的乐趣同时不至于劝退。可调。

### 5.4 升级（R5）

- 人头阈值 **每级新增 1/2/4/8**（等价于**累计 1/3/7/15**）：每次击杀给击杀者 +1 人头，达到阈值即升级，**人头跨战斗累计不清零**。
  例：2 级需 1 个、3 级需 3 个、4 级需 7 个、5 级需 15 个（**全场最多约 15 个敌人** → 5 级是跨多场才能达到的稀有状态；4v4 单场最多拿 4 个人头）。
  **实现口径（必须与 `spec_rules.md` §8.1 一致）**：`UnitData.kill_thresholds_cumulative = [1,3,7,15]`，只做一次比较 `kills >= thresholds[level-1]`。
  **备选**：`LEVEL_THRESHOLD_MODE="per_level_reset"`（存 `[1,2,4,8]` 并每级清零 `kills`），两者数学等价；**不要**把 `[1,2,4,8]` 当累计阈值用（那样满级只需 8 杀，是另一套曲线）。
- 最高 **5 级**，每级 **+3 点属性**，共 12 点。
- 可选属性池：力量 / 护甲 / 精力上限 / 破甲伤害 / 休息恢复力量 / 休息恢复护甲（+ 远程单位"射程" / 弹道单位"落地命中判定范围"）。
- **升级时点**：击杀**当场**弹出升级提示，但属性点分配**延后到战斗结束的结算面板**统一分配（战斗中不打断节奏；且存档只需存"待分配点数"）。两者都可配置（§11 Q4）。

### 5.5 回合顺序与胜负

> **本节以 `spec_rules.md` 的决策 D9 为准**（此前本文件写过"先攻值降序"，与规格冲突，已修正）。

- **回合结构 = IGOUGO（我方阶段 → 敌方阶段）**：一回合 = 玩家阶段 + 敌方阶段，双方各行动一次。玩家在自己阶段内**自由决定己方单位的操作顺序**（每个单位最多 1 次移动 + 1 次主动行动）；AI 阶段按规格 §4.4 的顺序逐个操作。
- **v1 单位没有"先攻值"属性**（`spec_rules.md` §9.2 的数值表不含该列）。因此：`data_schema.md` 的 `initiative` 字段与"先攻排序行动条"**已移除**；UI 顶部改为"阶段指示（我方/敌方）+ 剩余未行动单位数"。
- **削弱先手优势的开关（Q11）**：把敌方阶段改为**与我方交错**（我方 1 人 → 敌方 1 人 → …）是**同一个实现上的一行配置**（`TURN_INTERLEAVE=true`）。实测镜像阵容下 IGOUPO 的先手方胜率 100%，所以 M8 调参时**应优先开启交错**；但如果实测回合数已经落在 3-6 区间，也可以不开（交错会让局面更难预测）。
- **胜负**：一方全部阵亡（**力量池归零**；护甲池归零不减员）→ 另一方胜利；超时（> 30 回合）按存活数 → 池总和 → 平局判定（规格 §7）。
- 关卡可附加条件（v1 第 3 关用"守住 N 回合"）——**注意 `spec_rules.md` §7 尚未定义 `SURVIVE_ROUNDS`/`REACH` 的判定细节，这是 M2 开工前要补的一处规格缺口**（见 `docs/verification_report.md`）。
- 敌人 AI（v1）：效用评分——对每个可达格子 × 每个可打目标 × 力量或破甲 × 精力投入 打分（期望伤害、是否击杀、站位安全度、**距离衰减项**），取最高分执行；**任何情况下都必须移动 + 做一个动作，绝不站桩**（实测站桩 AI 胜率 0%）；目标护甲池已归零时，破甲选项分值置 0。**不做搜索树**（v1 不需要，且慢）。

## 6. 存档设计（R14）

| 项 | 设计 |
|---|---|
| 位置 | `user://saves/slot_N.json`。**Web 导出下 `user://` 由 Godot 映射到 IndexedDB 上的虚拟文件系统**（官方 data_paths 文档），`FileAccess` 代码无需任何改动 |
| 格式 | **JSON（人可读、可 diff、可手工修）**；数值内部一律用整数千分比（点 × 1000） |
| 内容 | **必须以 `spec_rules.md` §12 的字段清单为准**，含：`schema_version`/`rules_version`、`created_at/saved_at`、**`prng_state`（LCG 状态，uint32）**、**`balance_hash` + `rules_config_hash`**、关卡 id 与棋盘（`board_w/h`、`tiles[].h`）、阶段与行动方（`phase`/`turn_side`/`round`）、单位全量状态（**`P_max`/`P_cur`、`A_max`/`A_cur` 必须分开存**；精力 `EP`/`EPmax`、**`energy_used_this_turn`**（防存读档重置"每回合 3 点"额度）、`kills` 累计 + **`kills_this_level`**、`level`、`unspent_points`、位置与朝向、`has_moved_this_turn`/`has_acted_this_turn`）、双方阵亡记录、`battle_result`、玩家进度（已通关关卡、队伍编成）、设置项 |
| 单位数值的两种口径 | `P_max/A_max` 是**上限**（来自原型 + 升级加点），`P_cur/A_cur` 是**当前池**（被打掉后的值）。休息恢复到 `P_max`（钳制），升级上限校验用 `P_max`。二者**分开存**，不要用一个字段兼两义 |
| 槽位 | 3 个手动槽 + 1 个自动存档槽；自动存档时机 = 战斗开始、每回合结束、战斗结算后 |
| 原子性 | 先写 `slot_N.json.tmp` 再 rename，避免写一半断电损坏 |
| 兼容 | `migrations.gd`: `{"1": func(d): ...}` 迁移表；读档时若 `version` 高于当前程序则拒绝并提示 |
| **防丢档（硬需求，不可省）** | Web 下存档会因**清站点数据 / 无痕模式 / 浏览器磁盘驱逐 / 换设备 / iframe 嵌入且禁用第三方 cookie** 而永久丢失（官方明文列出的场景）。因此**必须**做：① 首次进入游戏与每次通关后提示"存档在浏览器里，建议导出备份"；② **存档导出/导入字符串**（压缩 + Base64 + 校验和）；③ 启动时尝试 `navigator.storage.persist()`；④ 检测到不可持久化时显式告警并引导"在新窗口打开" |
| 剪贴板 | 官方提示"从 GDScript 访问剪贴板 API 可能不可靠"，所以导出**不要只依赖复制按钮**——给一个**可全选的 `TextEdit`** 让用户手动复制/粘贴 |
| 配额 | 对本项目**完全不是问题**（存档只有几 KB；Chromium 约 60% 磁盘、Firefox `min(10%, 10GiB)`、WebKit 80%） |
| 防作弊 | v1 不做（单机），仅做校验和防止手改崩档 |

**为什么不用 Godot 的 `ConfigFile`/二进制**：JSON 便于调试、迁移和跨版本，且体积对这些数据量（<100 KB）完全够。

| P=10, A=6, 物抗=无(0) | D=4×1.0=4 → 造成 **4** 点 |
| P=10, A=10, 任意物抗 | delta=0 → **无法造伤**（该单位必须切破甲线；PvE 里玩家可回档，见 §0.5 C6） |

`save_service` + 迁移 + 存读档 UI + 主菜单/选关/设置 + **存档导出/导入字符串** + Web 与桌面导出 + 本机 Web 静态服务器实测。
**AC**：3 关全流程可玩；中途存档退出 → 重启 → 读档 → 状态完全一致（含 RNG 与待分配点）；导出包在 Chrome 打开可玩；**清站点数据后能用存档码恢复进度**；导出预设确认 `Use Threads = 关闭`。

### M8 调参与打磨（0.5-1 周）
`balance_sim` 跑 200 场；按 §7 的平衡目标调 `balance.tres`；补音效占位（可用 Godot 生成的简单音，或留空）；写操作说明与开发说明。
**AC**：平均回合数 3-6；胜率 40-60%；无卡死对局；README 能让"未来的自己"在 30 分钟内跑起来。

**总计约 7.5-8.5 周（6-10 h/周）**；其中 **M0.5 用 3-5 天换来：第一周就能试玩规则、且不依赖任何大体积下载**。

## 9. 风险登记册（Top 8）
